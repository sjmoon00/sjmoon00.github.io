쿼리는 왜 디스크가 아니라 버퍼 풀부터 만날까?

InnoDB 쿼리는 디스크가 아니라 버퍼 풀부터 만난다. 변형 LRU, Free/LRU/Flush List, 더티 페이지가 만들어지는 과정과 함께 지연 쓰기, 휘발성, Partial Page Write 문제를 정리했다.

“MySQL에 INSERT 한 건을 보내면 DB 안에서는 어떤 일이 일어날까?” 라는 질문에 답하기 위해 InnoDB 내부를 단계별로 정리한다.

이 글에서는 “문제” 까지를 다룬다.

1. MySQL 아키텍처#

스토리지 엔진을 보기 전에 MySQL의 전체 구조부터 살펴보자.

MySQL은 크게 MySQL 엔진과 스토리지 엔진으로 나뉜다.

  • MySQL 엔진: 쿼리 파싱, 최적화, 실행 계획 생성을 담당한다. 비유하면 운전자에 해당한다.
  • 스토리지 엔진: 데이터를 실제로 읽고 쓰는 일을 담당한다. 비유하면 자동차에 해당하며, 운전자(MySQL 엔진)가 사용하는 핸들(Handler API)을 제공한다.

SQL이 처리되기까지#

쿼리 한 건이 처리되는 큰 흐름은 다음과 같다.

  1. 애플리케이션이 커넥션 풀에서 커넥션을 가져온다. 기존 연결이 없다면 TCP 3-way handshake로 새로 연결한다.
  2. 쿼리가 MySQL 엔진에 전달된다.
  3. 파서가 쿼리를 최소 단위(토큰)로 나누고 문법을 검사한다.
  4. 전처리기가 테이블명, 컬럼명의 존재 여부와 접근 권한을 확인한다.
  5. 옵티마이저가 가장 효율적인 실행 방법을 결정하고 실행 계획을 만든다.
  6. 실행 엔진이 계획에 따라 스토리지 엔진을 호출한다.
  7. 결과를 클라이언트에 반환한다.

이 글에서는 3~5단계를 정상 통과했다고 가정하고, 6단계에서 스토리지 엔진(InnoDB)에 도달한 이후를 살펴본다.

2. 디스크에 바로 쓰지 않는 이유#

스토리지 엔진에 도달한 쿼리는 디스크 파일로 곧장 가지 않고 버퍼 풀을 먼저 거친다. 이유는 메모리와 디스크의 속도 격차다.

지연 시간의 차이#

대략적인 규모는 다음과 같다.

저장 장치접근 지연 시간(대략)
메모리(RAM)수십~수백 나노초
SSD수십~수백 마이크로초
HDD수 밀리초

장치와 환경에 따라 다르지만, 메모리와 디스크 사이에는 수백~수만 배 이상의 격차가 있다. (※ 위 수치는 일반적인 규모이며, 정확한 값은 장치 사양에 따라 다르다.)

랜덤 I/O vs 순차 I/O#

  • 테이블과 인덱스는 B+Tree 구조로 디스크 곳곳에 흩어져 있다.
  • 쿼리가 올 때마다 디스크의 특정 위치를 찾아가 수정하면 랜덤 I/O가 계속 발생한다.
  • 초당 수천 건 이상의 트랜잭션을 처리하는 시스템이 이 방식을 쓰면 디스크 I/O가 병목이 된다.

버퍼 풀의 해결 방식#

  • 디스크의 데이터 파일과 인덱스 페이지를 메모리에 캐싱해 두고, 읽기와 쓰기를 메모리에서 먼저 처리한다.
  • 버퍼 풀 크기는 innodb_buffer_pool_size로 설정한다. 일반적인 권장값으로 시스템 메모리의 50~75% 를 제시한다.

3. 버퍼 풀의 기본 단위#

버퍼 풀은 메모리를 임의로 쓰지 않고, 디스크 페이지와 대응되는 고정 크기 블록으로 나누어 관리한다.

페이지 (Page)#

  • InnoDB가 디스크와 메모리 사이에서 데이터를 주고받는 최소 단위다.
  • 기본 크기는 16KB다.
  • 레코드 1건만 조회해도 그 레코드가 속한 페이지 전체를 메모리에 올린다.

페이지 프레임 (Page Frame)#

  • 페이지 하나를 담을 수 있도록 버퍼 풀에 미리 나누어 둔 빈 슬롯이다.

제어 블록 (Control Block)#

  • 각 프레임에 대한 메타데이터다. 어느 테이블스페이스의 몇 번 페이지인지, 수정되었는지, 잠금 상태는 어떤지를 기록한다.

4. 버퍼 풀의 캐시 교체 정책: 변형 LRU#

버퍼 풀의 메모리는 유한하지만 디스크의 데이터는 계속 늘어난다. 풀이 가득 차면 기존 페이지 하나를 내보내야 새 페이지를 올릴 수 있다.

순수 LRU의 문제: 풀 스캔에 의한 캐시 오염#

  • mysqldump, 배치 작업, WHERE 절이 없는 대량 조회가 실행되면 수많은 페이지가 한꺼번에 버퍼 풀로 올라온다.
  • 순수 LRU는 새로 읽은 페이지를 무조건 리스트 맨 앞에 넣는다. 그래서 오래 자주 쓰이던 핵심 페이지가, 한 번 읽고 다시 쓰이지 않을 페이지 때문에 밀려나는 캐시 오염이 발생한다.

해결: 두 개의 sublist로 나눈 LRU#

InnoDB는 LRU 리스트를 하나의 큐가 아니라 두 개의 sublist로 나누어 관리한다.

[ Head (가장 최근 사용) ]                                    [ Tail (퇴출 대상) ]
 ┌───────────────────────────────────────┬──────────────────────────────────────┐
 │       New Sublist (5/8, 약 62.5%)     │       Old Sublist (3/8, 약 37.5%)    │
 └───────────────────────────────────────┴──────────────────────────────────────┘
 ▲                                       ▲                                      ▲
 Head                                 Midpoint                                 Tail
                                  (신규 페이지 삽입 지점)
  • New Sublist (Young 영역): 최근 자주 쓰인 페이지가 머무는 영역이다. 기본 5/8을 차지한다.
  • Old Sublist: 퇴출 후보가 머무는 영역이다. 기본 3/8을 차지한다.
  • Midpoint: 디스크에서 새로 읽은 페이지는 Head가 아니라 두 영역의 경계(Old Sublist의 Head)에 삽입된다.

승격 조건#

  • Midpoint에 들어온 페이지는 곧바로 New 영역으로 가지 못한다.
  • 풀 스캔은 한 페이지 안의 레코드를 연속으로 읽기 때문에, 단순히 “다시 참조되었다"는 것만으로 승격시키면 스캔 한 번에 캐시가 오염된다.
  • 그래서 페이지가 읽힌 뒤 일정 시간(기본 1,000ms)이 지난 후에 다시 참조될 때 비로소 New Sublist의 Head로 승격된다.
  • 한 번 스캔되고 버려지는 페이지는 Old Sublist의 Tail로 밀려나 조용히 퇴출되므로, 핵심 캐시가 보존된다.

5. 버퍼 풀 내부의 세 가지 리스트#

InnoDB는 버퍼 풀의 페이지를 효율적으로 관리하기 위해 세 가지 리스트를 둔다.

Free List#

  • 데이터가 담기지 않은 빈 페이지 프레임 목록이다.
  • 서버가 막 시작된 때에는 대부분의 프레임이 여기에 있고, 디스크에서 페이지를 읽을 때마다 하나씩 꺼내 쓴다.

LRU List#

  • 앞서 설명한 캐시 교체에 쓰이는 목록이다.
  • 디스크에서 올라온 모든 페이지가 머물며, 사용 빈도와 시간에 따라 교체 우선순위가 정해진다.

Flush List#

  • 수정이 발생해 디스크의 원본과 내용이 달라진 더티 페이지만 모은 목록이다.
  • 언젠가 디스크와 동기화되어야 하는 페이지들이다.
  • 가장 최근에 수정된 순이 아니라, 페이지가 처음 수정된 시점의 LSN(Log Sequence Number) 순으로 정렬된다. 이 순서가 있어야 체크포인트를 안전하게 앞으로 진행시킬 수 있다.

6. 더티 페이지는 어떻게 만들어지는가#

클라이언트가 INSERT INTO users ...를 보냈을 때, InnoDB 내부의 메모리 변경 흐름은 다음과 같다.

Handler API (write_row)
       │
       ▼
1. 버퍼 풀 탐색 (B+Tree로 대상 페이지 식별 → 해시 테이블로 버퍼 풀 존재 확인)
       ├── 메모리에 있음: 해당 페이지 프레임 획득
       └── 메모리에 없음: Free List에서 프레임 확보 후 디스크에서 16KB 읽어 적재
       │
       ▼
2. 메모리 페이지의 레코드 슬롯에 데이터 쓰기 (In-Memory Modification)
       │
       ▼
3. 상태 전환: Clean Page ──▶ Dirty Page
       │
       ▼
4. Flush List에 등록 (가장 오래된 변경 LSN 기준 정렬)

※ 실제로는 이 과정에서 undo log와 redo log 기록도 함께 일어난다. 2편에서 다룬다.

6-1. 페이지 위치 탐색#

  • 클러스터링 인덱스(B+Tree)를 따라 새 레코드가 들어갈 리프 페이지 번호를 찾는다.
  • 버퍼 풀 내부 해시 테이블로 그 페이지가 메모리에 있는지 확인한다.
    • 있으면 곧바로 페이지를 사용한다.
    • 없으면 Free List에서 빈 프레임을 받아 디스크에서 읽어온다.
    • Free List가 비어 있으면 LRU List의 Old Sublist 끝에 있는 페이지를 내보내야 한다. 이때 내보낼 페이지가 더티라면, 먼저 디스크로 flush한 뒤에야 프레임을 재사용할 수 있다. (메모리 확보가 디스크 I/O에 묶이는 지점이다.)

6-2. 메모리 수정#

  • 프레임 내부의 빈 슬롯에 레코드 데이터, 트랜잭션 ID, 롤 포인터를 기록한다.
  • 롤 포인터는 변경 이전 버전을 가리키는 undo 정보와 연결된다. (MVCC의 핵심이다.)

6-3. 더티 페이지 등록#

  • 수정된 페이지는 디스크와 내용이 달라졌으므로 더티 페이지가 되고, Flush List에 연결된다.

7. 메모리와 디스크를 맞추는 일은 왜 어려운가#

여기까지가 “빠르게 처리하는 방법"이었다면, 이제부터는 그 대가로 생기는 문제다.

7-1. 지연 쓰기는 피할 수 없다#

  • 변경마다 디스크에 동기화하면 랜덤 I/O 때문에 처리량이 크게 떨어진다.
  • 그래서 스토리지 엔진은 디스크 동기화를 최대한 미루고, 메모리에 모아 두었다가 백그라운드에서 한꺼번에 쓰는 전략을 택한다.

7-2. 메모리는 휘발성이다#

  • 클라이언트에 성공 응답을 보낸 시점에도, 수정된 데이터는 휘발성인 버퍼 풀에만 있을 수 있다.
  • 이 상태에서 전원이 나가거나 커널 패닉이 나면 더티 페이지는 사라진다.
  • 그렇다면 커밋된 데이터도 유실될까? 그렇지 않도록 InnoDB는 데이터 페이지보다 먼저 redo log를 디스크에 기록하고(커밋 시 redo log flush), 재시작할 때 이를 이용해 복구한다. 이 설계가 WAL(Write-Ahead Logging) 이며 다음에 다룰 주제다.

7-3. 하드웨어의 원자성 한계 (Partial Page Write)#

  • OS와 디스크가 보장하는 물리적 쓰기 단위는 보통 512바이트 또는 4KB다.
  • 반면 InnoDB 페이지는 16KB다.
  • 더티 페이지를 디스크에 쓰다 전원이 나가면, 페이지의 일부만 쓰인 손상된 페이지가 남을 수 있다. 이를 Partial Page Write라고 부른다.
  • 이 문제를 막기 위한 장치가 Doublewrite Buffer이며, 역시 다음에 다룬다.

정리#

메모리와 디스크 사이의 문제는 세 가지로 요약된다.

문제원인다음 편의 해결책
지연 쓰기성능을 위해 디스크 반영을 미룸체크포인트, 백그라운드 flush
휘발성메모리에만 있는 변경이 전원 장애로 소실redo log (WAL)
부분 쓰기페이지(16KB) > 하드웨어 원자 단위doublewrite buffer
